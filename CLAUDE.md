# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

RedCheck API is the Spring Boot backend for RedCheck, a task-prioritization app. It exposes a REST API consumed by a separate React frontend (`redcheck-frontend`), and offloads AI-based task prioritization to an external "SmartCheck AI" engine (a separate Python/FastAPI service, RAG-backed by Gemini) reached over HTTP. The frontend and the SmartCheck AI engine live in sibling repos and are sometimes relevant here — e.g. changing the `EngineRequestDTO` payload shape or the `/api/v1/prioritize` contract requires a coordinated change on the SmartCheck AI side, and DTO/response shape changes can affect the frontend. Flag this kind of cross-repo impact when it comes up.

## Commands

Use the Maven wrapper (`./mvnw`), not a system-installed Maven.

```bash
./mvnw spring-boot:run          # run the app locally (needs env vars, see below)
./mvnw clean package            # compile, run tests, and package the jar
./mvnw test                     # run the full test suite
./mvnw test -Dtest=TaskServiceTest                       # run a single test class
./mvnw test -Dtest=TaskServiceTest#shouldCreateTask       # run a single test method
```

JaCoCo is wired into the `test` phase (`mvn test`), producing a coverage report under `target/site/jacoco/`.

There is no linter/formatter configured in this repo.

### Running locally

The app reads all config through env vars referenced in `src/main/resources/application.yaml` — there is no committed `application-local.yml`/`.properties` (it's gitignored). At minimum you need: `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET`, `AI_ENGINE_URL`. Optional: `DDL_AUTO`, `SHOW_SQL`, `CORS_ALLOWED_ORIGINS`, `GOOGLE_CLIENT_ID` (the OAuth Client ID's audience for verifying Sign-in-with-Google ID tokens — see "Sign in with Google" below; without it, `/auth/google` always rejects tokens, since an empty audience never matches), `RESEND_API_KEY`/`MAIL_FROM`/`FRONTEND_URL` (Resend HTTP API config for password-reset emails — see "Forgot/reset password" below; without `RESEND_API_KEY` the app still starts fine, sending just fails at send-time and is logged, not thrown), `ADMIN_EMAILS` (who can open the developer dashboard and receives new-feedback emails — see "Developer dashboard" below; empty = nobody). Swagger UI / OpenAPI docs are disabled by default (`springdoc.api-docs.enabled=false`) — flip via env/profile if needed.

**Schema changes — there is no Flyway/Liquibase in this project.** `application.yaml` defaults `spring.jpa.hibernate.ddl-auto` to `validate`, but every actual docker-compose that runs this backend (the workspace-root one, `redcheck-infrastructure/docker-compose.yml`, and the production compose deployed via CI) sets `SPRING_JPA_HIBERNATE_DDL_AUTO=update`. So Hibernate's own schema-update-on-startup *is* the migration mechanism, in dev and in prod alike — adding/changing an entity field is enough, no separate migration file needed. When a new column must be `NOT NULL` on a table that may already have rows (like `Task.priority`, added 2026-09-09), give it a `columnDefinition` with a SQL `DEFAULT` (e.g. `"VARCHAR(20) DEFAULT 'MEDIUM'"`) — without one, Hibernate's generated `ALTER TABLE ... ADD COLUMN ... NOT NULL` has no way to backfill existing rows and errors on any table that isn't empty.

Docker: multi-stage `Dockerfile` builds with Maven then runs on a non-root user in `eclipse-temurin:17-jre-alpine`, exposing 8080. CI (`.github/workflows/deploy.yml`) builds/tests on push to `main`, pushes the image to Docker Hub, and deploys over SSH via `docker compose`.

## Architecture

Standard layered structure under `com.redcheck.backend`: `controller` → `service` → `repository` (Spring Data JPA) → `entity`, with `dto/{request,response,update}` used to keep entities off the wire. Controllers never receive/return entities directly.

### Domain model

`User` owns four collections cascaded with `orphanRemoval`: `Subject`, `Task`, `RecurringTask`, `Notification`, `AiResponse`, `ProgressRecord` — data is always scoped per-user. `Subject` → `Task` is also a cascading one-to-many. Ownership is enforced in the service layer (see `*NotOwnedException` classes), not by query filtering alone — when adding endpoints, verify the resource's owner matches `currentUser` before acting on it.

Soft-delete ("Trash") is a real field (`deletedFalse`/`deleted` filters appear throughout repository queries), not JPA `@Where`/`@SQLDelete`. Endpoints have `DELETE /{id}` (soft) and `DELETE /{id}/force` (hard) variants, plus `PATCH /{id}/restore`. `TrashCleanupSchedulerService` purges soft-deleted records on a schedule.

**Custom exceptions** (`exception` package: `TaskNotFoundException`, `TaskNotOwnedException`, `SubjectAlreadyExistsException`, etc.) are plain `RuntimeException` subclasses with no `@ResponseStatus` and there is no `@ControllerAdvice`/global exception handler anywhere in the app — they are not currently mapped to HTTP status codes at a central point. Keep this in mind when adding new failure cases; check how existing controllers/tests expect these to surface before assuming Spring maps them for you.

**Dashboard aggregate endpoint (`GET /subjects/with-tasks`):** fixes an N+1 the frontend used to have — it used to call `GET /subjects` then one `GET /subjects/{id}/tasks?completed=false` per subject. `SubjectService#getAllSubjectsWithTasks` instead does exactly two queries total (`SubjectRepository#findAllByUserAndDeletedFalse` + the new `TaskService#getPendingOrTodayTasks`, which reuses the existing `findPendingOrCompletedTodayAndDeletedFalse` query without the in-memory `subjectId` filter `TaskService#getAllTask` applies) and groups tasks by `subjectId` in memory (`Collectors.groupingBy`), returning `List<SubjectWithTasksResponseDTO>` (a `SubjectResponseDTO` shape plus a nested `tasks` list). If the dashboard ever needs a different task subset (e.g. all tasks, not just pending/completed-today), extend this pair rather than reintroducing a per-subject loop on the frontend.

**Task priority:** `Task.Priority` (`LOW`/`MEDIUM`/`HIGH`, `@Enumerated(EnumType.STRING)`, nested enum — same pattern as `AiResponse.Type`) defaults to `MEDIUM` both at the DB level (`columnDefinition = "VARCHAR(20) DEFAULT 'MEDIUM'"`, see the schema-changes note above) and via `@Builder.Default`, so any `Task.builder()...build()` call that doesn't set it (including `RecurringTaskSchedulerService`'s generated occurrences) still gets a valid value. `TaskRequestDTO.priority()` is optional on the wire: `TaskService#createTask` treats a null request priority as "default to MEDIUM", `#updateTask` treats it as "keep the task's current priority" (a null there is *not* "reset to MEDIUM") — this lets older/partial clients keep working without having to send it.

**Calendar history endpoint (`GET /tasks?from=YYYY-MM-DD&to=YYYY-MM-DD`):** a top-level endpoint (`TaskCalendarController`, deliberately *not* nested under `/subjects/{id}`, same N+1-avoidance reasoning as the dashboard endpoint above) that returns every task — pending **or completed** — across all of the user's subjects whose `deadline` falls within the given range, via `TaskService#getTasksForDateRange` and the new repository method `findAllBySubject_User_IdAndDeadlineBetweenAndDeletedFalse`. This exists because `findPendingOrCompletedTodayAndDeletedFalse` (used by the dashboard) only ever covers *today's* pending/completed tasks — it has nothing for a task that was completed on some earlier day, which is exactly what the frontend calendar needs for past-day history. `from`/`to` are both required and inclusive; the frontend fetches one range per visible calendar view (a single day, a week, or a whole month) rather than one call per day.

**Global routines endpoint (`GET /recurring-tasks?active=`, 2026-09-09):** another top-level, not-nested-under-`/subjects/{id}` endpoint (`RecurringTaskOverviewController`), same N+1-avoidance reasoning — it's what the frontend's global "all my routines" overview (across every subject) fetches in one call. It's not new service logic: `RecurringTaskService#getAllRecurringTask` already accepted an optional (nullable) `subjectId` to filter by — the pre-existing nested `RecurringTaskController` (`/subjects/{subjectId}/recurring-tasks`) just never had a way to invoke it with `subjectId = null`, since the path variable is always present there. This controller calls the exact same service method with `subjectId = null`. Response DTOs don't carry the subject's name — the frontend already holds the full `subjects` list in `DashboardPage.tsx` state and joins `subjectId` → name/color locally rather than denormalizing it onto every routine.

### Authentication

Stateless JWT (`io.jsonwebtoken`), configured in `security/`: `JwtService` (issue/parse/validate tokens), `JwtAuthenticationFilter` (a `OncePerRequestFilter` that reads the `Authorization: Bearer` header, skips `/auth/**`, and populates `SecurityContextHolder`), `SecurityConfig` (stateless session policy, permits `/auth/**` and Swagger paths, requires auth on everything else — including `/users/**` explicitly). `@AuthenticationPrincipal User currentUser` is the standard way controllers get the caller's identity. CORS origins come from `app.cors.allowed-origins` and are also referenced per-controller via `@CrossOrigin(origins = "${app.cors.allowed-origins}")`.

**Login accepts either email or username** (`LoginRequestDTO.emailOrUsername`) — `AuthService#login` resolves it to a `User` via `UserRepository#findByEmailOrUsername` (one query, `OR`'d across both columns, both already `unique = true` on the entity) *before* calling `authenticationManager.authenticate(...)`, then always authenticates with the resolved **email** — Spring Security's own `UserDetailsService` bean (`ApplicationConfig#userDetailsService`) is still keyed on email only (`User#getUsername()` returns `email`, per the class's own "use email for authentication instead of username" comment), so that part didn't need to change. If no user matches the identifier, `login` throws `BadCredentialsException` itself (same exception type a wrong password produces) rather than letting a `NoSuchElementException`/different failure leak through — keeps "no such user" indistinguishable from "wrong password" in the response, avoiding a user-enumeration side channel. `AuthService#register` now checks `existsByUsername` alongside the pre-existing `existsByEmail` check, for the same reason username uniqueness matters here: it's now a login credential, not just a display name.

**Sign in with Google (2026-09-10):** `POST /auth/google` (`GoogleAuthRequestDTO.idToken`) accepts a Google Identity Services ID token from the frontend and verifies it entirely offline — `GoogleTokenVerifierService` wraps `com.google.api.client.googleapis.auth.oauth2.GoogleIdTokenVerifier` (from the `google-api-client` dependency), checking the signature against Google's published public keys plus audience (`app.google.client-id`, env `GOOGLE_CLIENT_ID`)/issuer/expiry — no call out to Google on the request path, and no client secret involved anywhere in this flow, since it only needs to confirm who the token is for, not exchange an authorization code. This is a deliberately separate, much simpler mechanism than the still-paused Google Calendar sync (see frontend `CLAUDE.md`'s "Pending" note) — Calendar sync needs an authorization-code OAuth flow with a client secret and Google's sensitive/restricted-scope app verification; Sign-in only requests `openid`/`email`/`profile`, which Google classifies non-sensitive and never requires verification for, even for a published production app.

`User.password` is now nullable and `User.googleId` (nullable, unique) was added — `AuthService#loginWithGoogle` resolves an incoming Google identity in priority order: match by `googleId` first; if none, match by `email` and link the existing password-based account (sets `googleId` on it — this is what lets someone who registered with a password start also using "Sign in with Google" for the same account, without violating the unique email constraint by inserting a second row); if neither matches, create a brand-new `User` with `password = null`. `generateUniqueUsername` derives a username from Google's `name` claim (falling back to the email's local part), lowercased and stripped to `[a-z0-9]`, disambiguated against `existsByUsername` with a numeric suffix if needed — Google never supplies a username, but the column is still `NOT NULL UNIQUE` on `User`. A Google-only user (`password == null`) simply can't succeed at the existing password `login` endpoint — `BCryptPasswordEncoder.matches` treats a null encoded password as a non-match rather than throwing, so it fails the same ordinary way a wrong password would, no special-casing needed. `emailVerified` on the Google token is required to be `true`, or the login is rejected as `InvalidGoogleTokenException` — an unverified Google email must never be trusted to link/create a `User` row.

**Forgot/reset password (2026-09-10):** `POST /auth/forgot-password` (`ForgotPasswordRequestDTO{email, lang}`) always responds `200` with no body **regardless of whether the email is registered** — a deliberate user-enumeration guard, same reasoning as `AuthService#login`'s "no such user" vs "wrong password" indistinguishability. `PasswordResetService#forgotPassword` does the actual work only `if` the email matches a user **and** that user has a password (`user.getPassword() != null` — a Google-only account has nothing to reset, and silently no-op'ing there is unobservable from outside since the controller's response never varies). On a match: any of that user's still-unused tokens are deleted first (`PasswordResetTokenRepository#deleteUnusedByUser` — only the most recently requested link ever works), a new `PasswordResetToken` (random UUID, 30-minute expiry, `used=false`) is saved, and `EmailService#sendPasswordResetEmail` is called — `@Async` (mirrors `SmartCheckAIService`'s fire-and-forget external call; `@EnableAsync` already on) and internally try/catches its own send failures (logged, never thrown), so a broken SMTP config can never turn into a 500 on this endpoint or roll back the token row. `POST /auth/reset-password` (`ResetPasswordRequestDTO{token, newPassword}`) validates the token exists, isn't expired (`PasswordResetToken#isExpired`) and isn't already used, then updates the user's password and flips `used=true` — same `InvalidResetTokenException` → controller-catches-directly → `400` pattern as `UserController`'s `InvalidCurrentPasswordException`. `PasswordResetTokenCleanupSchedulerService` sweeps expired/used tokens hourly, same cron pattern as `TrashCleanupSchedulerService`. `PasswordResetToken.user` is `@OnDelete(action = OnDeleteAction.CASCADE)` (unlike `Feedback.user`'s deliberate `SET_NULL` — a reset token is meaningless once its user is gone, so it should vanish with them, not get orphaned). **Email sending is via Resend's HTTP API (`POST https://api.resend.com/emails`, `RestTemplate`, `Bearer ${RESEND_API_KEY}` auth — `EmailService`), not SMTP.** This was a deliberate rework, not the original design — see the incident notes below for why. `ResendEmailRequestDTO{from, to, subject, html}` mirrors the shape `SmartCheckAIService` already uses for its own external POST calls (a typed DTO in `dto/request`, `RestTemplate` instantiated inline per call, no shared bean — same convention). **The user is using Resend**, not Brevo, despite Brevo being the original choice: Brevo's free/non-Enterprise plan silently rewrites transactional SMTP emails (injects open/click-tracking pixels, rewrites every link through its own redirect domain, adds a `List-Unsubscribe` header), confirmed via Brevo's own community forum to have no self-service way to disable on non-Enterprise plans — this showed up as Gmail treating the email as bulk mail (extra UI chrome, e.g. requiring a click to expand the full message) and, worse, silently replacing the reset link with a tracking-redirect URL. `EmailService`'s HTML template has the app's brand lockup at the top (`icon-192.png` + "REDCHECK" wordmark, table-based layout for email-client compatibility — matches `LoginPage.tsx`'s header) plus one accent color and a single CTA button, deliberately minimal to match the frontend's own clean/minimal visual language rather than a heavier marketing-style email. The logo's `<img src>` is built from `app.frontend.url` + `/icons/icon-192.png` (the frontend serves that file as a static PWA icon asset already) — in local dev where `FRONTEND_URL=http://localhost`, the logo won't actually render in a received email since Gmail's servers can't reach `localhost`; this is expected and only resolves once `FRONTEND_URL` is a real public URL in production. **DMARC:** `redcheckapp.com` needed an explicit `_dmarc` TXT record (`v=DMARC1; p=none; rua=mailto:dmarc-reports@redcheckapp.com`) added in DNS — without one, Gmail reported `DMARC: FAIL` even with SPF and DKIM both passing and aligned, which is likely what triggered Gmail's extra scrutiny/UI treatment of the message.

**Incident (2026-09-10): SMTP dropped in favor of Resend's HTTP API after production silently couldn't send any password-reset email.** The feature worked in local testing (Docker Desktop-style environment) but every production attempt logged `EmailService`'s "Sending password reset email to..." line and then just hung forever — no success log, no error, nothing. Diagnosed via `openssl s_client` run directly on the production VPS: `openssl s_client -starttls smtp -connect smtp.resend.com:2587` (and separately, implicit-TLS `-connect smtp.resend.com:2465` with no `-starttls`) both showed `CONNECTED` (the TCP handshake completes) but the remote SMTP server never sends its banner — confirmed the same dead silence on ports 25/465/587/2465/2587 via plain `nc -zv`. This is the VPS provider's network silently black-holing outbound SMTP-destined traffic (allows the TCP handshake, drops everything after) — not a JavaMail config issue, not something fixable by picking a different port, and something that would almost certainly have broken Brevo too (SMTP was never actually tested from *this* server before switching providers, only from a local machine). Since the app already makes outbound HTTPS calls fine (Gemini, the AI engine), routing email through Resend's REST API instead of raw SMTP sidesteps the block entirely rather than fighting it. `spring-boot-starter-mail` was removed from `pom.xml` (no longer used) along with all `spring.mail.*` config in `application.yaml`; `MAIL_HOST`/`MAIL_PORT`/`MAIL_USERNAME`/`MAIL_PASSWORD` env vars are dead — replaced by a single `RESEND_API_KEY` (`app.resend.api-key`). `MAIL_FROM`/`FRONTEND_URL` are unchanged. **If forgot-password email ever goes silent again in some future deployment, check outbound HTTPS to `api.resend.com` first (should always work if the rest of the app's external calls do) before assuming it's a code regression** — a provider/environment that blocks outbound port 443 broadly would need a different fix (e.g. an HTTP proxy), but that's a much rarer network posture than SMTP-port blocking.

**Change/set password (2026-09-10):** `PATCH /users/me/password` (`UserController#changePassword`, `ChangePasswordRequestDTO{currentPassword, newPassword}`) lets an authenticated user change their password — or, for a Google-only account (`password == null`), set one for the first time. `UserService#changePassword` re-fetches the user by email (same pattern as `deleteUser`, not trusting the `@AuthenticationPrincipal`-injected entity to still be attached) and only checks `currentPassword` when `user.getPassword() != null`; a Google-only account skips that check entirely (there's nothing to verify against) and just sets the new password. A wrong `currentPassword` throws `InvalidCurrentPasswordException`, the one exception in this codebase a controller catches directly (`UserController` maps it to `400`) rather than letting it fall through to the framework's default `500` — deliberate, since the frontend needs to distinguish "wrong current password" from a generic failure for this form. `newPassword` has one manual guard (`>= 8` chars, throws plain `IllegalArgumentException` otherwise, same "no Jakarta Validation on this DTO" style as `RegisterRequestDTO`) — falls through to `500` like `AuthService#register`'s duplicate-email case, an already-accepted pattern in this codebase. `GET /users/profile` (`UserResponseDTO`) now also returns `hasPassword` (`currentUser.getPassword() != null`) so the frontend can tell a "change password" account from a "set a password" (Google-only) one without a separate call. **Demo-account guard (fixed same day, was initially missing):** the two seeded demo accounts (`demo-es@redcheck.com`/`demo-en@redcheck.com`, see `DataInitializer`) are shared, publicly reachable identities — changing the one password they all rely on would lock out every other demo user. `util/DemoAccountUtils#isDemoAccount` is the single source of truth for the two emails (not yet used by `UserController#deleteMyAccount`'s own pre-existing, separately-hardcoded pair of checks — left untouched to avoid touching already-working code, but any *new* demo-account check should go through this util instead of a third hardcoded copy). `UserService#changePassword` throws `DemoAccountRestrictedException` for a demo account (checked before the new-password-length check) — `UserController` catches it and returns `403`, with the same bilingual-by-specific-email message convention `deleteMyAccount` already uses. `PasswordResetService#forgotPassword` silently no-ops for a demo account (same pattern as the Google-only-account check just above it — the controller's response never varies, so this isn't observable), and `resetPassword` additionally re-checks `DemoAccountUtils.isDemoAccount` on the token's owner as defense-in-depth (covers a token that might have been issued before this guard existed), rejecting it as just another invalid token via the existing `InvalidResetTokenException` rather than a distinct error. **New password must differ from the current one (2026-09-10, `UserService#changePassword` only — not the forgot/reset-password flow, scoped that way on request):** checked right after the current-password verification, via `passwordEncoder.matches(newPassword, user.getPassword())` — only when `user.getPassword() != null` (a Google-only account setting its first password has nothing to compare against). Throws `NewPasswordSameAsCurrentException`, mapped by `UserController` to `409` (deliberately not `400`, so the frontend can tell "wrong current password" and "new password same as old" apart by status code alone, without parsing the English-only message body).

### User feedback

`Feedback` (`category`: `BUG`/`SUGGESTION`/`PRAISE`/`OTHER`, `message`, `user`, `createdDate`, plus `status`/`adminNote` for triage — see "Developer dashboard" below) is created via `POST /feedback` and read/triaged only through the developer dashboard's `/admin/feedback` endpoints. It's the one User-linked entity deliberately **not** cascaded from `User`'s `orphanRemoval` collections: deleting a user must never fail because they once submitted feedback, and the product team wants to keep that data even after the account is gone. Instead `Feedback.user` uses `@OnDelete(action = OnDeleteAction.SET_NULL)` (nullable FK, DB-level `ON DELETE SET NULL`) — if this pattern needs reuse elsewhere for the same reason (keep the row, drop the link), copy it rather than adding another cascaded collection to `User` (`AiUsageLog.user` does exactly this).

### Developer dashboard (`/admin/**`, 2026-10-17)

A private, admin-only API backing the frontend's `/developer` page. **Access:** `ADMIN_EMAILS` env var (`app.admin.emails`, comma-separated, case-insensitive; empty by default = nobody) read by `AdminAccessService` — deliberately an allowlist, not a role column on `User`, since there's a single admin. `SecurityConfig` gates `/admin/**` with an `access(...)` rule calling `AdminAccessService#isAdmin`; that rule is the real enforcement. `GET /users/profile` also returns `isAdmin` so the frontend can show/hide the entry point — cosmetic only. `AdminControllerIntegrationTest` is the one controller test that `@Import`s the real `SecurityConfig` (mocking `AuthenticationProvider`), precisely to cover that rule; when stubbing `isAdmin`, match on the email (`argThat`), never on a `User` instance — `User`'s `@EqualsAndHashCode(onlyExplicitlyIncluded = true)` has no included fields, so every `User` is `equals()` to every other one and an instance-based stub silently returns `true` for everybody.

- **Feedback triage:** `Feedback.status` (`NEW`/`SEEN`/`IN_PROGRESS`/`DONE`/`WONTFIX`, `VARCHAR(20) DEFAULT 'NEW'` so `ddl-auto=update` can add it to a non-empty table) and `adminNote` (TEXT, nullable, never shown to the user). `GET /admin/feedback` returns everything newest-first (`FeedbackRepository#findAllByOrderByCreatedDateDesc`, `@EntityGraph` on `user` to avoid an N+1) as `AdminFeedbackResponseDTO` (author email/alias, null once the author deleted their account); filtering is client-side. `PATCH /admin/feedback/{id}` (`AdminFeedbackUpdateDTO`) is a partial update — null = unchanged, blank note = clear it; a missing id → `FeedbackNotFoundException`, caught in `AdminController` → `404`.
- **New-feedback email:** `FeedbackService#createFeedback` calls `EmailService#sendNewFeedbackNotification` (`@Async`, Resend, same fire-and-forget contract as the reset email) for every address in `ADMIN_EMAILS`, passing plain values (never the entity — it runs on another thread). The user-supplied message is HTML-escaped (`HtmlUtils.htmlEscape`) and whitespace-collapsed for the subject. There's no rate limit: a user spamming `POST /feedback` would also spam the admin inbox and burn Resend quota — acceptable at current scale, revisit if it happens.
- **In-app reply to the author:** `POST /admin/feedback/{id}/notify` (`FeedbackReplyRequestDTO{message}`, `@NotBlank`, max 255 — `Notification.message` is a plain `VARCHAR(255)`) creates a `Notification` of type `FEEDBACK_REPLY` for `feedback.user` and stamps `Feedback.userNotifiedDate`; with `sendEmail: true` it also emails the same text via `EmailService#sendFeedbackReplyEmail` (from `MAIL_FROM`, the no-reply address — the template says replies go nowhere and quotes the user's original message, both HTML-escaped; `lang` picks the template language). `sendEmail` is a nullable `Boolean` on purpose — Jackson 3 fails on a missing primitive, so a `boolean` would turn a request that omits it into a `400`; `404` for a missing feedback, `409` (`FeedbackAuthorDeletedException`) when the author deleted their account. `Notification` gained `type` (`SYSTEM`/`FEEDBACK_REPLY`, `VARCHAR(30) DEFAULT 'SYSTEM'` — every pre-existing row and every SmartCheck AI notification is `SYSTEM`). `GET /notifications` accepts an optional `type` filter (`NotificationService#getNotificationsByType`, newest first; without `type` the old untyped behavior is unchanged), and `PATCH /notifications/{id}/read` marks one read (looked up by id **and** owner via `findByIdAndUser`, so another user's notification is a plain `404`). Until this, nothing in the frontend ever read backend notifications — the bell only showed a local "AI plan ready" flag — so the frontend deliberately lists only `FEEDBACK_REPLY`, not the backlog of English-only, never-marked-read `SYSTEM` rows. The `title` stored for a reply is a fixed marker (`"Feedback reply"`); the frontend shows its own localized heading.
- **Users (`GET /admin/user-stats?days=`, `UserStatsService`):** two independent notions of "active", both excluding the demo accounts (`DemoAccountUtils`) and the admins themselves. **Seen** = had an authenticated request: `User.lastSeenAt`, written by `UserActivityService` (`@EventListener` for `UserSeenEvent`, published by `JwtAuthenticationFilter` after a successful auth) via a targeted `UserRepository#updateLastSeenAt` UPDATE, and only when the in-memory value is >1h stale — so most requests cost no write, and a failure is logged, never thrown. It's an event instead of injecting the service into the filter on purpose: the filter is loaded by every `@WebMvcTest` slice, and a new constructor dependency there would break all of them. Exact, but only from deployment onwards, and with no per-day history (only each user's latest value). **Acting** = did something real: `TaskRepository#findCompletionActivitySince` (completed a task) + `#findManualCreationActivitySince` (created one by hand — `recurringTask IS NULL`, since scheduler-generated occurrences get an `assignedDate` the user never set); deleted tasks are kept. Approximate, but from existing data, so it has full history — `daily` is activity-based for that reason. Aggregated in memory, same as AI usage.
- **System (`GET /admin/system`, `SystemStatusService`):** which build is running (`BuildProperties` from `spring-boot-maven-plugin`'s `build-info` goal — version + build time; plus `app.git-sha` = `APP_GIT_SHA`, baked into the image by the `Dockerfile`'s `GIT_SHA` build arg, which CI sets to `${{ github.sha }}` — `unknown` for local/compose builds), JVM uptime/memory, and a ping to the engine's `GET /health` with a 3s connect/read timeout (null latency = down). Exists so "is this fix actually deployed?" is answerable at a glance — see the custom-frequency incident note below.
- **AI usage:** `AiUsageLog` (one row per outbound call to the engine — `PRIORITIZE` or `TASK_OUTCOME`, `success`, `durationMs`, `taskCount`, nullable `user` with `SET_NULL`) is written by `SmartCheckAIService` around the HTTP call only, via `AiUsageService#record` — `REQUIRES_NEW` + its own try/catch so a failed log write can never roll back or break the AI flow. Kept separate from `AiResponse` on purpose: `AiResponse` only holds the latest successful analysis (re-running deletes today's previous one) and never records failures. `GET /admin/ai-usage?days=30` (clamped 1–90) returns `AiUsageStatsResponseDTO`, aggregated in memory with one entry per day (zeros included). Real Gemini token counts aren't available here — the engine doesn't return `usage_metadata` yet, and it retries `generate_content` up to 3× internally, so one `PRIORITIZE` row = 1–3 generate calls + 1 embedding; each `TASK_OUTCOME` = 1 embedding. Exposing tokens would be a coordinated change with `smartcheck-ai-engine`.

### Recurring tasks & schedulers

`RecurringTask.frequency` is a plain `String` with no dedicated schema for structure — it's one of 4 simple presets (`DAILY`/`WEEKLY`/`BIWEEKLY`/`MONTHLY`), a custom day-of-week pattern, or a custom monthly-day pattern, and `FrequencyUtils` is the single place that understands all three. `isSimple(frequency)` picks the first branch; `nextExecution(frequency, from)` does `from.plusX(...)` for presets, `nextMonthlyDayExecution` for `MONTHLY_DAY_PATTERN` matches, or — for anything else — `CronExpression.parse(frequency).next(from)` (`org.springframework.scheduling.support.CronExpression`, built into Spring Framework, no extra dependency). A custom day-of-week frequency is always a 6-field cron string shaped `"0 0 0 * * <days>"` (seconds/minutes/hours pinned to midnight, since `RecurringTaskSchedulerService` only ticks once a day anyway; `<days>` a comma-separated list of 0-6, Sunday=0, matching JS `Date#getDay()`) — built and parsed on the frontend via `recurrenceUtils.ts` (`buildCustomFrequency`/`parseCustomFrequencyDays`/`formatCustomFrequencyLabel`), used by both `SubjectSection.tsx`'s create form and `RecurringTasksModal.tsx`'s inline edit form (`WeekdayPicker.tsx` is the shared day-chip UI). A custom monthly-day frequency is `"MONTHLY:<day>"`, `<day>` 1-31 or the literal `"LAST"` — deliberately **not** cron, since Spring's `CronExpression` has no Quartz-style `"L"` (last-day-of-month) character, and a plain numeric day-of-month cron field would silently skip short months (day 31 never firing in February) instead of clamping to that month's real last day; `nextMonthlyDayExecution`/`clampToMonth` handle both rules by hand with `java.time.YearMonth`. `RecurringTaskRequestDTO.frequency`'s `@Pattern` is deliberately narrower than a generic cron-charset regex — it only accepts the 4 presets or exactly those two custom shapes, so every stored frequency the API will ever accept can always be parsed back into the right editor UI (day checkboxes or a day-of-month picker); don't loosen it to accept arbitrary cron (arbitrary month fields, letter-based day names, etc.) without also building UI that can display/edit whatever gets added. `RecurringTaskSchedulerService.generateTask()` wraps each recurring task's processing in its own try/catch — one bad/unparseable `frequency` (e.g. stale data from before this validation existed) logs and is skipped rather than aborting generation for every other active recurring task in that run. `RecurringTaskSchedulerService` generates the next `Task` occurrences; `ProgressRecordSchedulerService` computes recurring progress snapshots. Both run via Spring's `@Scheduled` (`@EnableScheduling` is on in `RedCheckApiApplication`).

**Routine streaks and completion stats (2026-09-09):** `RecurringTaskResponseDTO` carries `currentStreak`/`longestStreak`/`completionRate`/`totalGenerated`/`totalCompleted`, all computed fresh on every read by `RecurringTaskService#computeStats` from `TaskRepository#findAllByRecurringTaskAndDeletedFalseOrderByAssignedDateAsc` — deliberately **not** persisted/incremental counters, since a routine's full occurrence history is always small (at most one `Task` per day since it began) and computing from scratch can never drift out of sync with reality the way a cached counter could (e.g. after a past occurrence is manually deleted, or its completion is toggled back off). `currentStreak` counts consecutive completed occurrences from the most recent one backwards, and is **0 the instant the latest occurrence isn't completed yet** — there's deliberately no "grace period" heuristic for "today's task, not due yet" vs. "yesterday's task, missed"; keeping the rule simple and honest was judged better than a heuristic that would sometimes guess wrong. `longestStreak` is the best run anywhere in the full history, not just the current tail. `completionRate` is `0.0` (not `null`) when nothing's been generated yet — a routine with no history isn't "unknown," it's "0% so far."

**Recurring task time-of-day and end date (2026-09-09):** `RecurringTask` also carries optional `time` (`LocalTime`) and `endDate` (`LocalDate`), both nullable — null preserves the original behavior exactly (no deadline on generated tasks, runs forever). When `time` is set, `RecurringTaskSchedulerService#generateTask` sets the newly-created `Task`'s `deadline` to `LocalDate.now().atTime(time)` — before this, every generated task had **no** deadline at all, so a routine's tasks never actually showed up scheduled anywhere in the calendar/day view. When `endDate` is set, the scheduler enforces it two ways: `isAfterEndDate` (strictly after — the day of `endDate` itself is still a valid final occurrence) short-circuits generation entirely and deactivates the routine as a safety net (for a missed run); `hasReachedEndDate` (on-or-after) runs immediately *after* a successful generation to deactivate the routine right away if that occurrence was its last, rather than waiting for the next day's safety-net check. Don't collapse these into one `>=`/`>` check — the off-by-one between them is exactly what lets `endDate` generate its final occurrence instead of stopping one day too early. `RecurringTaskResponseDTO.nextOccurrence` is a read-only preview (`RecurringTaskService#computeNextOccurrence`, never mutates state) of when the routine will next fire, mirroring the scheduler exactly (see "Custom-frequency generation fix" below): before any generation, it's `FrequencyUtils#firstOccurrenceOnOrAfter(frequency, tomorrow)` — tomorrow for a simple preset, the first selected day for a custom pattern; once `latestGeneratedDate` is set, the frequency is stepped forward from it until the date is after today (so a paused/edited routine never previews a past date). Returns `null` for an inactive routine or once the projected date would fall after `endDate`.

**Custom-frequency generation fix (2026-10-17, after a user report that custom routines generated on the wrong days):** two separate bugs in `RecurringTaskSchedulerService#shouldGenerate`, both only affecting custom weekday/day-of-month frequencies. (1) **Gaps:** it used to compare `now` against a single `nextExecution(latestGeneratedDate)`, so after any gap (routine paused and reactivated, its days edited, a missed midnight run) the next tick generated immediately on whatever day it was. `isDueToday` now steps `nextExecution` forward until it's no longer in the past and only returns true if that lands exactly on today; the "previous occurrence still pending → don't duplicate" check now runs only on a genuinely due day and no longer bumps `latestGeneratedDate`. (2) **First occurrence:** a never-generated routine (`latestGeneratedDate == null`) used to generate on the very first tick regardless of pattern (a Mon/Thu routine created on a Tuesday got a Wednesday task); it now generates only when `FrequencyUtils#firstOccurrenceOnOrAfter(frequency, today)` is today. Simple presets (`DAILY`/`WEEKLY`/…) have no pattern of their own and still start on the first tick. **`RecurringCalendarEventSchedulerService` had the exact same two bugs** (it was written by mirroring the task scheduler) and is fixed the same way. The rule now lives in one place, `FrequencyUtils#nextOccurrenceOnOrAfter(frequency, latestGeneratedDate, date)` (null `latestGeneratedDate` → `firstOccurrenceOnOrAfter`; otherwise step `nextExecution` forward until not before `date`) and `#isDueOn` (that, `== date`) — both schedulers call `isDueOn(…, today)` and both `nextOccurrence` previews call `nextOccurrenceOnOrAfter(…, tomorrow)`, so they can't drift apart again; don't reintroduce a local copy of the walk in either. The frontend's `getUpcomingOccurrences` (shared by both routine editors via `RecurrenceFieldset`) mirrors the same rules. Fix (1) sat uncommitted on a dev machine for weeks while the user had already been told it was fixed — if a "fixed" bug is reported again, check what's actually deployed first.

### SmartCheck AI integration

`SmartCheckAIService.runDailySmartAnalysis` is `@Async` (`@EnableAsync` is on): it gathers the user's pending tasks plus per-subject completion-ratio analytics from `TaskRepository`, posts them as `EngineRequestDTO` to `${ai.engine.url}/api/v1/prioritize` via `RestTemplate`, and persists the raw JSON response as an `AiResponse` (type `DAILY_ANALYSIS`), creating a `Notification` on success or failure. Results are fetched later via `getTodaysAnalysis` (only returns a result if it was created today) — the AI call itself is fire-and-forget from the controller's perspective. `lang` is passed through so the external engine can localize output.

**Guard: `POST /ai/analyze` rejects a user with zero pending tasks (2026-09-10, fixed a real hang):** asking the AI engine to prioritize an empty task list made `runDailySmartAnalysis` (and the engine itself) hang indefinitely — no result ever got persisted, so the frontend's `pollForAnalysis` polled for its full ~3 minutes before timing out with a generic error, and worse, a request sent straight at the API (bypassing the frontend's own button/command-palette entirely) had nothing stopping it. `SmartCheckAIService#hasPendingTasks(User)` (`!taskRepository.findAllBySubject_User_IdAndCompletedDateIsNullAndDeletedFalse(userId).isEmpty()`) is checked synchronously in `SmartCheckAIController#dailySmartAnalysis` **before** `deleteTodaysAnalysis`/the `@Async` `runDailySmartAnalysis` call ever fires — a `400 Bad Request` short-circuits the request there, so the hang can no longer happen regardless of what a caller sends on the wire (this endpoint takes no task list as part of its payload to begin with; tasks are always re-read fresh from the DB inside the service, so there was never a "corrupt payload" to validate — the fix is a server-side precondition check, not request-body validation). The frontend (`redcheck-frontend`'s `Sidebar.tsx`/`DashboardPage.tsx`) independently disables/hides its own entry points when `totalPending === 0`, but this backend check is the one that actually can't be bypassed.

### Tests

Tests live flat under `src/test/java/com/redcheck/backend` (no sub-packages), pairing `*ServiceTest` (Mockito-based unit tests) with `*ControllerIntegrationTest` (`@WebMvcTest` + `MockitoBean` for services/`JwtService`, `MockMvc` for HTTP-level assertions, Jackson via `tools.jackson.databind.ObjectMapper`). There's no `@SpringBootTest`-with-real-DB integration layer — controller tests mock the service layer, so they don't exercise JPA/DB behavior. This is the intended style: keep writing new tests as mocked-service unit/`@WebMvcTest` pairs rather than introducing a real-DB integration layer (e.g. Testcontainers).
